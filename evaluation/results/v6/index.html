Asking for readable Elixir

Astra and Sol · 18 runs · Three per model and effort · 8 Sep 2026

Run data

Sweat Bench asks a coding agent to build GroupStay, a hotel-deposit application, through seven changing requests. The application must keep working as new features arrive and old databases are upgraded. The earlier Astra and Sol runs often concentrated much of that work in a few large modules. This experiment repeats the task with an instruction to write clear, idiomatic Elixir, without suggesting an architecture or naming the earlier failures.

Astra earned full marks in all nine runs at medium, high and xhigh, and one of three at low. Sol earned full marks in one of three runs at each effort. Astra consistently divided the application into smaller modules, but two low runs still repeated an earlier migration mistake. Sol's code was often more modular too, while its failures ranged from reconstructing old payments to correcting financial reports. More modular code did not consistently mean fewer failures.

The instruction

This text was appended to the normal request at all seven milestones. Each milestone still began a fresh model session. The agent inherited its own repository and tests, but could not see earlier benchmark runs, future requirements, the private tests or their results.

The requirements and deterministic scoring remain v6. There are three attempts at each of six configurations, and all 18 are included. The instruction was verified in all 126 milestone sessions. No run received private evaluation feedback or an analyst's repairs.

Astra used the same CLI version (0.153.4), runner and Docker image as its earlier runs. Sol used that environment too, whereas its earlier runs used older CLIs on macOS. The shared host VM also had more capacity than in the Astra baseline campaign; each candidate kept its two-CPU, 4-GiB limit. The comparison uses three historical controls per Astra effort and five per Sol effort. It was not randomized, and the controls were not run concurrently with the intervention.

Code structure

Astra gives more responsibilities their own names and modules. Low separates booking policy, payment history and room-funding backfill. High separates reservation commands from the durable record of each request, then divides finance into state collection, journal entries and reports. These divisions survive the later milestones instead of being folded back into one large module.

The documentation often explains a rule that matters to the implementation. Astra Low's Operations module describes why a request, its effects and its saved response share one transaction. Astra X-High's request parser explains why revision checks must precede some other validation. Astra High's finance module gives the reader an account of how reporting begins and later periods close.

The largest production file is 269–434 lines across the twelve intervention Astra runs, compared with 506–843 across its twelve controls. Even the two failing low runs split their work into smaller files. Sol High's largest files are 875–1,044 lines, below all five of its controls at 1,480–2,255. Sol Medium is less uniform: its largest files range from 975 to 1,802 lines. Run 2 has the smallest largest file at that setting, yet also the lowest score.

Median production code grows at every setting: 17–21% for Astra, 9% for Sol Medium and 28% for Sol High. Median API-equivalent costs rise 9–17% for Astra and fall 19–26% for Sol. Sol takes longer in both settings, while Astra xhigh is faster on average than its controls. These are observed differences, with Sol's environment change making a prompt-only explanation particularly uncertain.

Astra: storage and restarts

Reading rooms from an older database

Milestone 4 adds accounting for individual rooms. Its database migration must read the bookings created by milestone 3 and assign their existing funding to rooms. Four baseline Astra runs misread the stored room list: the database contained JSON strings inside another JSON array, but the migration expected room objects after a single decode.

Low runs 2 and 3 repeat that mistake. Run 2 reads the database with raw SQL; run 3 uses an Ecto query without a schema. Neither gets the typed decoding an Ecto schema would provide. Their test fixtures insert room objects directly as JSON, so the tests agree with the new reader but not with the old application's stored data. The real upgrade fails before it can assign funding to rooms.

On disposable copies, adding the missing inner decoding makes both complete upgrade tests pass for each run. That one repair accounts for the two lost points in each result. Low run 3 later catches the same decoding problem in its transfer migration and fixes it there, but leaves the earlier room migration unchanged.

The ten passing runs use three alternatives. Low run 1 uses Ecto's typed loader; medium run 3 keeps old schema definitions inside the migration. Medium runs 1 and 2, high runs 1 and 3, and xhigh run 3 use embedded rooms whose JSON contains objects after one decode. High run 2 and xhigh runs 1 and 2 store rooms as separate rows. Each reader matches what its own earlier version wrote.

The distinction is not simply SQL versus Ecto. Raw SQL works with the embedded representation; a schema-free Ecto query still exposes the nested strings. Successful baseline runs already used typed loading, embedded rooms, separate rows or an explicit second decoding step. The maintainability instruction did not make any one of these choices inevitable.

Returning a saved response after a restart

A partner can send the same payment or reporting request more than once. GroupStay must return its original answer without applying the operation again, even after the server restarts. Six baseline runs failed while rebuilding that saved answer. They converted JSON keys into Elixir atoms whose existence depended on another module having loaded first.

All twelve intervention runs pass this boundary. Seven return JSON-shaped saved responses: low runs 1 and 3, medium runs 2 and 3, and all xhigh runs. The other five keep an explicit list of response keys in the decoding module itself. Neither approach needs finance to have run first. A separate audit retried saved requests as the first HTTP operation after a fresh server start: all twelve returned the exact original result, while the same probe reproduced the six baseline failures.

High run 1 shows how the explicit list can expose an omission. At milestone 6, its own test retried a request and failed because starts_on was missing. The agent added the field and kept the exact-response assertion. The missing definition failed during an ordinary test, without needing a particular server startup state. Medium run 1 also switched to an explicit key map, but no recorded failure prompted that edit.

What their tests establish

Restart coverage varies. All low runs restart database connections inside an already-running Elixir VM. Several higher-effort runs start separate processes, though not always with finance requests. Medium run 2, high run 2 and xhigh runs 1 and 3 include finance in their process tests; xhigh run 2 also performs a manual HTTP restart rehearsal. The independent evaluator checks the actual fresh-server boundary in every run.

High run 2 and xhigh run 3 catch another real problem this way: a closed report contains the same values after restart, but its JSON fields appear in a different order. Their cross-process tests compare the encoded report, not just the decoded values. Both agents add deterministic field ordering before delivery. More demanding tests helped here; other runs pass the saved-response checks with narrower tests because their storage design avoids the original dependency.

An additional accounting check

A separate, unscored probe asks what happens when a payment is charged back with a date before the credit expired, after that expiry has already appeared in a closed report. The open report should withdraw that credit and undo its earlier expiry. Those entries cancel in the balance but describe different events.

Low run 1 and all three xhigh runs retain both entries; the other eight intervention runs omit both. All twelve preserve the closed report and reach the same zero balance. The successful implementations keep the transaction's original date separate from its later reporting date. X-High run 2's journal makes that distinction explicit, and its own test checks both entries. Two baseline runs also preserve the pair. This probe follows the requirements for signed transaction categories, but is outside the frozen scored examples and does not change any published result.

Sol: history, reporting and revisions

All six Sol runs store rooms as database rows and return saved JSON responses without relying on finance-module loading. They avoid Astra's two recurring representation mistakes. Their remaining failures concern different obligations: assigning old payments to the right rooms, correcting reports after close, advancing a booking's revision, and returning the expected expiry-date field.

Assigning old payments to rooms

Medium run 2 completes the room migration but puts all cash before all credit. The requirement preserves the order in which the recorded payments arrived. For example, if cash arrives, then credit, then more cash, the later cash must not jump ahead of the credit when funding is assigned to rooms. The totals can agree while individual rooms have the wrong funding.

Its own upgrade rehearsal printed the resulting room allocations without asserting the required order. The output already showed the mistake, but the agent accepted it. Medium run 3 instead combines cash and credit into one ordered history, then divides that history among rooms while retaining the original credit-lot identities. It passes both upgrade checks. Executing the two migrations' allocation SQL on the same isolated examples reproduces the wrong and right allocations respectively.

When a transaction arrives after the books close

GroupStay can issue hotel credit when a reservation is cancelled. Unused credit eventually expires, and the finance report records that reduction in what the hotel owes. Closing an accounting period freezes its reports. A partner may then submit an old-dated request to use credit that was still valid on the date of the transaction. The application must honor that date without rewriting the closed report: it records an expiry reversal in the first open period, restoring the credit liability there.

Medium runs 1 and 2 accept that credit use and preserve the closed report, but their expiry helpers only change entries that have not yet expired. They omit the correction once its reporting date falls after expiry. The first open report shows zero credit liability instead of 300 cents. A second test consumes the restored credit and finds the same missing reversal. These two scenarios cost three points in each run; medium run 2 also has the independent room-allocation error.

Both agents' own close tests cover late payments and new credit issuance, but never apply existing credit after a closed expiry. Their final suites pass all 47 and 52 tests. On disposable copies, adding the missing reversal makes all ten milestone-7 HTTP cases pass for each implementation. The original scores and sources remain unchanged.

Medium run 3 and all three high runs make the required correction. Medium run 3 adds an explicit negative-expiry entry. High run 2 also explicitly restores expired credit; high runs 1 and 3 reconcile the liability change with the recorded transaction categories and add the missing expiry adjustment.

Medium run 3 and high run 1 recognize this case during review after their existing tests pass. Each adds the correction and a targeted test before delivery. Medium run 3's test checks the restored liability, negative expiry and zero closing liability on the closed day. Removing its reversal on a disposable copy makes that test and the two private reporting cases fail. The tests genuinely cover the mechanism, even though the original discovery came from review rather than a red test.

A revision update that never reaches the database

Payments can fund rooms in another booking after a transfer. If that payment is reduced, the original booking's revision must advance even when only the destination loses money. High run 2 includes the original booking in its update set, but all its financial fields are unchanged. Ecto treats that as a no-op and skips the write, including the optimistic-lock increment. The response returns revision 3 where the request requires 4.

Its own test reduces enough money to affect both bookings, so the original booking does have changed fields and the test passes. High run 3 tests a reduction confined to the destination, sees the missing revision increment, and forces the revision update. Applying the same small correction to a copy of high run 2 makes the previously failing transfer case pass. Its two lost Core points come from an ordinary test and an upgrade test reaching the same revision error, not two separately established defects.

The expiry-date field

High run 3's remaining failure is narrower. It documents expires_on as the first day credit is unavailable and returns that date. The evaluator expects the last usable day. Both failing responses identify the correct remaining credit lot and amount; only the date differs. The early request leaves room for that interpretation, but milestone 6 explicitly makes the field the last usable date. The run keeps its original convention. A display-only change on an audit copy clears both assertions without changing eligibility or accounting. It loses one Core point and passes every Maintenance check.

The recurrence is specific. The missing report correction also appears in baseline medium run 1 and high run 4; the expiry-field convention appears in baseline medium run 4. All ten Sol controls pass the room-upgrade and transfer-revision checks that intervention medium run 2 and high run 2 fail. The intervention does not simply remove or preserve one fixed set of Sol weaknesses.

A balance can be right while its explanation is incomplete

The additional chargeback probe described for Astra was also executed against Sol High run 1. It kept the correct zero balance and unchanged closed report, but omitted both the credit revocation and its offsetting expiry reversal. Its net-liability reconciliation could not recover two missing entries that cancel each other out. That observation concerns this particular run and unscored sequence, not all six Sol implementations.

What this tells us

The clearest pattern is more modular organization, not a universal improvement in correctness. Astra medium and high each swept all three intervention runs, compared with zero and one of three controls. That is a promising result worth distinguishing from low, which repeated an old migration failure twice, and xhigh, which already swept all three controls.

Sol provides no similar improvement in sweep counts. Medium swept one of three, versus two of five controls; high swept one of three, versus four of five. High did pass every Maintenance check, but retained narrower failures in revision handling or the expiry-date field. Smaller modules made responsibilities easier to locate without ensuring that their interactions were correct.

The successful techniques were already present in some baseline runs. Three samples per setting, historical controls and the environment differences do not establish how much of the outcome the instruction caused. Nor do the failures establish that it has no effect. The experiment supports using a maintainability instruction to express the desired code style; it does not establish that the instruction reliably prevents the benchmark's recurring bugs. Readability observations and additional audit probes remain separate from the fixed scores.

About these findings

Sweat Bench tests how coding agents handle software that changes over time. Each agent builds GroupStay, a fictional application for managing hotel deposits for group reservations. Over seven milestones, it adds bookings, payments, cancellations, hotel credit, transfers and financial reports. Every new version has to keep the earlier features working and preserve the records they created.

Each run is a separate attempt at that sequence. The agent writes the code and its own tests. After each milestone, the benchmark tests the application, including what happens when the server restarts or a new version opens a database created by an earlier one.

To understand the results, we went back through the code, tests and session logs from all 77 completed runs in the Models tab. We looked for mistakes that recurred across runs, tests that caught them before delivery, and cases where one bug caused several checks to fail. The sections below follow each model family through those successes and failures.

The review covers small samples across 13 model families and several coding tools; the separate Harnesses experiments are excluded. Scores come from the accepted dataset. All seven code snapshots for each run are in the source archive; raw session logs remain private. Scoring details · Earlier retrospective

Note on expiry dates

The milestone-2 request described hotel credit this way:

The lot is available through the date 365 days after cancellation and expires the following day.

The tests expect expires_on to mean the last usable day; some implementations used the first unavailable day. Both describe the same usable period, but the wording leaves the field's meaning ambiguous. Milestone 6 made the last-usable-day meaning explicit. Scores retain the original evaluations.

These 30 completed Models runs returned the first unavailable day in their final version: Sol medium 4; GPT-5.6 Luna xhigh 2, 4, 5; Terra xhigh 1–4; GPT-5.5 xhigh 3, 4; Opus high 1; Muse Spark high 1; Grok 4.7 xhigh 1; Qwen xhigh 1, 3, 4; DeepSeek max 1, 4, 5; Kimi max 1; GLM 5.3 high 2–4; GLM-5.3 Flash high 1–3 and max 1–4.

The task

Sweat Bench asks a coding agent to build and maintain a small business application through seven milestones. Each milestone brings a new request. The agent has to make the change while keeping earlier features working and preserving data created by previous versions.

The application is GroupStay, a fictional service that manages hotel deposits for group reservations. It starts with bookings, payments and cancellations, then adds hotel credit, durable retries, room-level accounting, transfers, daily finance reports and period close. The agent writes a Phoenix/Elixir application backed by SQLite, starting from a service skeleton.

The sequence matters. A way of storing payments that works at launch may be inadequate once individual rooms can be cancelled or money moved between reservations. A report may show the right balance today but change incorrectly when a late adjustment arrives. The benchmark checks whether the agent carries those earlier decisions through the later changes.

Each milestone starts a fresh model session with the repository, current request, accumulated documentation and any tests the agent has written. It cannot see future requests or the evaluator's tests and results. After the agent finishes, the evaluator checks the HTTP API, restarts the application, and tests upgrades using databases from earlier milestones. The code and documents left in the repository are what the next session inherits.

The repository README describes all seven milestones and links to the requests. The source archive contains the generated applications at every milestone for all 102 accepted runs.

Scoring

Core out of 39
The requested features and business rules, including persistence, retries and upgrades. Related checks are grouped into 39 families. A family earns one point when all its checks pass.
Maintenance out of 10
Ten automated checks: five test upgrades of existing production data, and five test interactions among payments, credits, transfers and reporting.
Sweep
A run that earns all 39 Core points and all 10 Maintenance points.
Ship and final out of 94 scenarios
Ship counts scenarios passed when their milestone was delivered. Final counts them after later milestones, combining tests of the finished application with historical system checks recorded at the relevant milestone. Those historical checks are not rerun against the final code.
Recovery
The change from ship-time to final scenario totals. A positive value means later work repaired earlier failures; a negative value means regressions outnumbered repairs. Migration failures recorded at delivery still count even if the code is repaired later.

The runs

The Models view includes 77 runs that completed all seven milestones and passed the benchmark's integrity checks. Runs with low scores are included. Unfinished runs and runs with invalid evaluations are excluded. Each configuration has between one and five runs, so small differences in averages may not hold up with more samples. Chart ranges show the lowest and highest observed values, not confidence intervals.

A model runs through a coding tool, or harness, which also affects the result. Astra uses Codex CLI 0.153.4; GPT-6 Luna uses 0.155.1; earlier GPT runs used an older Codex version. The twelve Astra runs and three GPT-6 Luna runs used the standard v6 handoff prompts and launched no subagents. GPT-6 Luna had delegation disabled and no readability intervention. Opus 5 uses Claude Code 2.1.243 with customizations disabled. Grok 4.7 uses OpenCode 1.18.31. Muse Spark uses OpenCode 1.18.27; the harness comparison uses OpenCode 1.18.0.

Astra X-High runs 2 and 3 stopped on provider-capacity errors, then completed after restarting the interrupted milestone from the last accepted snapshot. No evaluation feedback was supplied. Their costs and runtimes include the discarded attempts; the time between stopping and restarting is excluded. The Astra results document both resumptions.

The Harnesses view includes 20 of the Codex runs from the Models view, 20 additional OpenCode runs and five Luna runs with the delegation instruction. There are 45 runs in that view, but 20 also appear in Models.

Cost accounting

Codex and Claude Code costs are API-equivalent: recorded token usage multiplied by the documented API rates. These runs used subscriptions, so the amounts are comparison costs, not additional subscription charges. OpenCode model costs are recorded OpenRouter charges, except GLM-5.3 Flash, whose free-preview usage is priced at its production rates. The Harnesses view uses API-equivalent costs throughout.

Costs include the main agent and all its subagents, as well as Codex's automatic review, priced at Luna rates. Reasoning tokens are included in output tokens and are charged only once. The private evaluator makes no model calls and adds no inference cost.

In the Astra runs shown here, the largest request contained 123,779 input tokens, below the 272K threshold for long-context pricing, and no cache-write tokens were recorded. GPT-5.5's recorded context window was 258,400 tokens. Some older logs lack enough detail to reconstruct per-request surcharges or cache-write charges, so those estimates use standard rates.

Codex includes cache reads in its total input count; OpenCode reports them separately. The calculations account for that difference. As an agent's conversation grows, repeatedly sending its history can become expensive even at cached rates: cache reads account for roughly $12–14 per Kimi run and $13–22 per GLM 5.3 run.

Model-specific accounting

GLM-5.3 Flash was tested as OX Alpha, a free preview. Its displayed costs apply the announced production rates to that preview usage. The two Opus subscription runs recorded $43.96 and $51.35 in API-equivalent usage. The OpenCode harness comparison used a subscription login and incurred no additional inference charges.

GPT-6 Luna uses $0.10 per million uncached input tokens, $0.01 per million cached input tokens and $0.50 per million output tokens. All 21 milestone sessions reconcile with their CLI usage totals. The largest request contained 175,697 input tokens; no long-context charges, cache writes or subagent sessions were recorded.

Muse Spark's $53.61 charge includes two automatic continuations after it reached the turn-length limit. DeepSeek run 2 includes $0.32 for a repeated review that made no code changes.

Code size and runtime

Code size counts lines in the finished application, including comments and blank lines. Production code covers lib/ and database migrations; test code covers test/. The table shows the median across runs, rounded to a whole line. Line counts describe the size of the implementation, not its quality.

Runtime adds up the time spent in agent sessions across the seven milestones, including reasoning, tool use, tests, continuations and interrupted attempts in completed runs.
