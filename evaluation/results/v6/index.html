The task

Sweat Bench asks a coding agent to build and maintain a small business application through seven milestones. Each milestone brings a new request. The agent has to make the change while keeping earlier features working and preserving data created by previous versions.

The application is GroupStay, a fictional service that manages hotel deposits for group reservations. It starts with bookings, payments and cancellations, then adds hotel credit, durable retries, room-level accounting, transfers, daily finance reports and period close. The agent writes a Phoenix/Elixir application backed by SQLite, starting from a service skeleton.

The sequence matters. A way of storing payments that works at launch may be inadequate once individual rooms can be cancelled or money moved between reservations. A report may show the right balance today but change incorrectly when a late adjustment arrives. The benchmark checks whether the agent carries those earlier decisions through the later changes.

Each milestone starts a fresh model session with the repository, current request, accumulated documentation and any tests the agent has written. It cannot see future requests or the evaluator's tests and results. After the agent finishes, the evaluator checks the HTTP API, restarts the application, and tests upgrades using databases from earlier milestones. The code and documents left in the repository are what the next session inherits.

The repository README describes all seven milestones and links to the requests.

Scoring

Core out of 39
The requested features and business rules, including persistence, retries and upgrades. Related checks are grouped into 39 families. A family earns one point when all its checks pass.
Maintenance out of 10
Ten automated checks: five test upgrades of existing production data, and five test interactions among payments, credits, transfers and reporting.
Sweep
A run that earns all 39 Core points and all 10 Maintenance points.
Ship and final out of 94 scenarios
Ship counts scenarios passed when their milestone was delivered. Final counts them after later milestones, combining tests of the finished application with historical system checks recorded at the relevant milestone. Those historical checks are not rerun against the final code.
Recovery
The change from ship-time to final scenario totals. A positive value means later work repaired earlier failures; a negative value means regressions outnumbered repairs. Migration failures recorded at delivery still count even if the code is repaired later.

The runs

The Models view includes 73 runs that completed all seven milestones and passed the benchmark's integrity checks. Runs with low scores are included. Unfinished runs and runs with invalid evaluations are excluded. Each configuration has between one and five runs, so small differences in averages may not hold up with more samples. Chart ranges show the lowest and highest observed values, not confidence intervals.

A model runs through a coding tool, or harness, which also affects the result. Astra uses Codex CLI 0.153.4; earlier GPT runs used an older Codex version. The twelve Astra runs shown here, three each at low, medium, high and X-High, used the standard v6 handoff prompts and launched no subagents. Opus 5 uses Claude Code 2.1.243 with customizations disabled. Muse Spark uses OpenCode 1.18.27; the harness comparison uses OpenCode 1.18.0.

Astra X-High runs 2 and 3 stopped on provider-capacity errors, then completed after restarting the interrupted milestone from the last accepted snapshot. No evaluation feedback was supplied. Their costs and runtimes include the discarded attempts; the time between stopping and restarting is excluded. The Astra results document both resumptions.

The Harnesses view includes 20 of the Codex runs from the Models view, 20 additional OpenCode runs and five Luna runs with the delegation instruction. There are 45 runs in that view, but 20 also appear in Models.

Cost accounting

Codex and Claude Code costs are API-equivalent: recorded token usage multiplied by the documented API rates. These runs used subscriptions, so the amounts are comparison costs, not additional subscription charges. OpenCode model costs are recorded OpenRouter charges, except GLM-5.3 Flash, whose free-preview usage is priced at its production rates. The Harnesses view uses API-equivalent costs throughout.

Costs include the main agent and all its subagents, as well as Codex's automatic review, priced at Luna rates. Reasoning tokens are included in output tokens and are charged only once. The private evaluator makes no model calls and adds no inference cost.

In the Astra runs shown here, the largest request contained 123,779 input tokens, below the 272K threshold for long-context pricing, and no cache-write tokens were recorded. GPT-5.5's recorded context window was 258,400 tokens. Some older logs lack enough detail to reconstruct per-request surcharges or cache-write charges, so those estimates use standard rates.

Codex includes cache reads in its total input count; OpenCode reports them separately. The calculations account for that difference. As an agent's conversation grows, repeatedly sending its history can become expensive even at cached rates: cache reads account for roughly $12–14 per Kimi run and $13–22 per GLM 5.3 run.

Model-specific accounting

GLM-5.3 Flash was tested as OX Alpha, a free preview. Its displayed costs apply the announced production rates to that preview usage. The two Opus subscription runs recorded $43.96 and $51.35 in API-equivalent usage. The OpenCode harness comparison used a subscription login and incurred no additional inference charges.

Muse Spark's $53.61 charge includes two automatic continuations after it reached the turn-length limit. DeepSeek run 2 includes $0.32 for a repeated review that made no code changes.

Code size and runtime

Code size counts lines in the finished application, including comments and blank lines. Production code covers lib/ and database migrations; test code covers test/. The table shows the median across runs, rounded to a whole line. Line counts describe the size of the implementation, not its quality.

Runtime adds up the time spent in agent sessions across the seven milestones, including reasoning, tool use, tests, continuations and interrupted attempts in completed runs. Time spent running the private evaluator, saving snapshots or advancing to the next milestone is excluded. The two resumed Astra X-High runs exclude stopped time. DeepSeek run 4 also excludes a documented 10h 52m machine interruption; time spent working before and after it is retained.

Subagents counts distinct agents started by the candidate. Built-in workers such as Codex's automatic reviewer are excluded from that count, but their token usage is included in the cost.
