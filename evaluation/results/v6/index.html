Asking for readable Elixir

Astra and Sol · Six runs · One per model and effort · 7 Sep 2026

Run data

Sweat Bench asks a coding agent to build GroupStay, a hotel-deposit application, through seven changing requests. The application must keep working as new features arrive and old databases are upgraded. The earlier Astra and Sol runs often concentrated much of that work in a few large modules. This experiment repeats the task with an instruction to write clear, idiomatic Elixir, without suggesting an architecture or naming the earlier failures.

All four Astra runs and Sol High earned every Core and Maintenance point. Sol Medium earned 38 out of 39 and 8 out of 10. The code shows different responses to the same instruction: smaller, more focused modules in Astra and Sol High, but a large central module in Sol Medium. The investigation follows how those implementations handle old data, server restarts and financial history.

The instruction

This text was appended to the normal request at all seven milestones. Each milestone still began a fresh model session. The agent inherited its own repository and tests, but could not see earlier benchmark runs, future requirements, the private tests or their results.

The requirements and deterministic scoring remain v6. All six configurations were recorded before the pilot started, and every completed attempt is included. The instruction was verified in all 42 milestone sessions. No run received private evaluation feedback or repairs after evaluation.

Astra used the same CLI version (0.153.4), runner and Docker image as its earlier runs. Sol used that environment too, whereas its earlier runs used an older CLI on macOS. The shared host VM also had more capacity than in the Astra baseline campaign. These are historical comparisons, with one intervention run per configuration, not a controlled measurement of the instruction's effect.

Code structure

Astra gives more responsibilities their own names and modules. Low separates booking policy, payment history and room-funding backfill. High separates reservation commands from the durable record of each request, then divides finance into state collection, journal entries and reports. These divisions survive the later milestones instead of being folded back into one large module.

The documentation often explains a rule that matters to the implementation. Astra Low's Operations module describes why a request, its effects and its saved response share one transaction. Astra X-High's request parser explains why revision checks must precede some other validation. Astra High's finance module gives the reader an account of how reporting begins and later periods close.

The largest production file is 288–403 lines in the intervention Astra runs, compared with 506–843 in its earlier runs. Sol High also spreads more code across smaller files: its largest is 875 lines, versus 1,480–2,255 in its five controls. Sol Medium is different. Its 1,802-line Deposits module still holds almost half its production code, within the range of its earlier implementations.

All six runs contain more production code than their corresponding historical medians. The costs do not move together: Astra costs 10–25% more, while Sol costs 12% less at medium and 29% less at high. Both Sol runs take longer than any of their same-effort controls. Their changed execution environment makes timing especially difficult to attribute to the instruction.

How Astra avoided its earlier failures

Reading rooms from an older database

Milestone 4 adds accounting for individual rooms. Its database migration must read the bookings created by milestone 3 and assign their existing funding to rooms. Four baseline Astra runs misread the stored room list: the database contained JSON strings inside another JSON array, but the migration expected room objects after a single decode.

The new runs avoid that mismatch in three ways. Low uses Ecto's typed loader, which reads the representation its schema wrote. Medium and high use embedded room records, whose stored JSON matches their migration's single decode. X-High stores rooms as separate database rows, so there is no nested room JSON to decode.

Their own upgrade tests still construct old data rather than launch the old application. The benchmark supplies that additional check: it creates bookings through the actual earlier version, upgrades the database, and checks the later behavior. All four pass. They are preserving their own history; they are not required to import databases from other runs.

Returning a saved response after a restart

A partner can send the same payment or reporting request more than once. GroupStay must return its original answer without applying the operation again, even after the server restarts. Six baseline runs failed while rebuilding that saved answer. They converted JSON keys into Elixir atoms whose existence depended on another module having loaded first.

Low and X-High remove that dependency by returning the saved JSON directly. Medium and high instead keep an explicit list of response keys in the decoding module itself. The decoder no longer depends on whether finance code has already run.

High provides the clearest example of a test catching an incomplete response definition. At milestone 6, its new reporting test retried a request and failed because starts_on was missing from that list. The agent added it, kept the exact-response retry assertion, and passed its tests. With the explicit list, a forgotten field failed during an ordinary test instead of depending on what happened to be loaded after a restart.

Medium also replaced a load-dependent decoder with an explicit key map during milestone 3, but no recorded failure prompted that edit. Low and X-High used direct JSON responses from the start of durable storage. The evidence therefore supports different routes to a correct implementation, not one repeated repair.

What their tests establish

Low and medium's finance tests restart database connections inside the same running Elixir VM. High starts fresh processes for earlier operation types, but its finance tests also use connection restarts. X-High extends fresh-process tests through reporting and period close. The private evaluator independently restarts the server and retries saved reporting requests before any report is read; all four pass those checks.

How Sol handled financial history

Both Sol runs passed every scored upgrade and restart check. They stored rooms as database rows from milestone 1 and returned saved JSON responses directly from milestone 3. Those choices avoid the two recurring Astra defects, but were also present in earlier Sol implementations. The difference between Sol Medium and High appears in the final reporting request.

When a transaction arrives after the books close

GroupStay can issue hotel credit when a reservation is cancelled. Unused credit eventually expires, and the finance report records that reduction in what the hotel owes. Closing an accounting period freezes its reports. A partner may then submit an old-dated request to use credit that was still valid on the date of the transaction. The application must honor that date without rewriting the closed report: it records an expiry reversal in the first open period, restoring the credit liability there.

This connects rules introduced at different milestones: credit eligibility, daily reporting and period close. Several earlier Sol runs missed the connection. The two intervention runs give a direct comparison of implementations that do and do not account for it.

Medium: one missing entry, three lost points

Medium accepted the old-dated credit request and preserved the closed report, but its expiry helper only adjusted an expiry that had not yet passed. Once the reporting date moved beyond it, the helper did nothing. The first open report consequently showed zero liability instead of 300 cents.

A second test used 600 cents of credit and then consumed it through a non-refundable cancellation. Medium recorded the consumption but omitted the offsetting expiry reversal. These two failed scenarios account for one Core point and two Maintenance points. On a disposable copy, adding the missing reversal made all ten milestone-7 HTTP cases pass, including both original failures. The published run remains unchanged at 38 Core and 8 Maintenance.

Its own period-close tests covered late payments and newly issued credit, but never applied existing credit after a closed expiry. All 47 candidate tests passed. The gap was in the interaction they omitted, not in a failing test the agent left unresolved.

High: review found the missing connection

High identified the closed-expiry case while reviewing milestone 7, after its first 59 tests had passed. It added a liability reconciliation and a targeted test in the same patch. The test closes a report containing an expiry, applies 600 cents using an earlier transaction date, then checks the expiry reversal and restored liability in the next period. All 60 tests passed.

The reconciliation records a signed expiry adjustment when the ordinary credit entries do not explain the change in liability. Removing that step on a disposable copy made the retained test fail: closing liability became zero instead of 600 cents. This confirms that the test exercises the repair, although the agent originally wrote the repair and test together rather than discovering it through a failed test.

High also made visible structural changes as the task grew. At milestone 5 it extracted transfer handling from room accounting; at milestone 6 it separated report queries from recording financial changes. Medium introduced a reporting module too, but left most other business behavior in its large Deposits context.

A balance can be right while its explanation is incomplete

An additional, unscored check found a narrower limitation in Sol High. After closing a credit expiry, the application received a chargeback dated while that credit was still valid. The reports kept the correct zero balance, but omitted both the credit revocation and its offsetting expiry reversal. A calculation based on the net change could not recover two missing entries that cancel each other out. The Astra X-High tests explicitly check that pair. This audit result is separate from the fixed v6 scores.

What this tells us

The strongest result is a change in how several implementations organize the work. All four Astra runs and Sol High assign more responsibilities to focused modules. Their passing upgrade, restart and late-credit cases have concrete explanations in the code. Sol Medium shows the limit of the same instruction: useful names and documentation coexist with a large central module and a missed accounting interaction.

The instruction did not introduce these successful techniques to the benchmark. Earlier runs already used compatible room storage, direct JSON responses and explicit expiry reversals. Astra X-High had swept all three controls; Sol High had swept four of five. One intervention run per configuration cannot establish whether the instruction makes those choices more likely, especially with Sol's changed execution environment.

The six runs therefore offer examples of clearer organization and specific successes and failures, not a measured reliability improvement. Costs rose for Astra and fell for Sol relative to their historical medians. A larger comparison with fresh runs both with and without the instruction would be needed to separate its effect from ordinary variation. Readability judgments and the extra audit checks remain outside the benchmark score.

About these findings

Sweat Bench tests how coding agents handle software that changes over time. Each agent builds GroupStay, a fictional application for managing hotel deposits for group reservations. Over seven milestones, it adds bookings, payments, cancellations, hotel credit, transfers and financial reports. Every new version has to keep the earlier features working and preserve the records they created.

Each run is a separate attempt at that sequence. The agent writes the code and its own tests. After each milestone, the benchmark tests the application, including what happens when the server restarts or a new version opens a database created by an earlier one.

To understand the results, we went back through the code, tests and session logs from all 73 completed runs in the Models tab. We looked for mistakes that recurred across runs, tests that caught them before delivery, and cases where one bug caused several checks to fail. The sections below follow each model family through those successes and failures.

The review covers small samples across 13 model families and several coding tools; the separate Harnesses experiments are excluded. Scores come from the accepted dataset. All seven code snapshots for each run are in the source archive; raw session logs remain private. Scoring details · Earlier retrospective

Note on expiry dates

The milestone-2 request described hotel credit this way:

The lot is available through the date 365 days after cancellation and expires the following day.

The tests expect expires_on to mean the last usable day; some implementations used the first unavailable day. Both describe the same usable period, but the wording leaves the field's meaning ambiguous. Milestone 6 made the last-usable-day meaning explicit. Scores retain the original evaluations.

These 29 completed Models runs returned the first unavailable day in their final version: Sol medium 4; Luna xhigh 2, 4, 5; Terra xhigh 1–4; GPT-5.5 xhigh 3, 4; Opus high 1; Muse Spark high 1; Qwen xhigh 1, 3, 4; DeepSeek max 1, 4, 5; Kimi max 1; GLM 5.3 high 2–4; GLM-5.3 Flash high 1–3 and max 1–4.

The task

Sweat Bench asks a coding agent to build and maintain a small business application through seven milestones. Each milestone brings a new request. The agent has to make the change while keeping earlier features working and preserving data created by previous versions.

The application is GroupStay, a fictional service that manages hotel deposits for group reservations. It starts with bookings, payments and cancellations, then adds hotel credit, durable retries, room-level accounting, transfers, daily finance reports and period close. The agent writes a Phoenix/Elixir application backed by SQLite, starting from a service skeleton.

The sequence matters. A way of storing payments that works at launch may be inadequate once individual rooms can be cancelled or money moved between reservations. A report may show the right balance today but change incorrectly when a late adjustment arrives. The benchmark checks whether the agent carries those earlier decisions through the later changes.

Each milestone starts a fresh model session with the repository, current request, accumulated documentation and any tests the agent has written. It cannot see future requests or the evaluator's tests and results. After the agent finishes, the evaluator checks the HTTP API, restarts the application, and tests upgrades using databases from earlier milestones. The code and documents left in the repository are what the next session inherits.

The repository README describes all seven milestones and links to the requests. The source archive contains the generated applications at every milestone for all 98 accepted runs.

Scoring

Core out of 39
The requested features and business rules, including persistence, retries and upgrades. Related checks are grouped into 39 families. A family earns one point when all its checks pass.
Maintenance out of 10
Ten automated checks: five test upgrades of existing production data, and five test interactions among payments, credits, transfers and reporting.
Sweep
A run that earns all 39 Core points and all 10 Maintenance points.
Ship and final out of 94 scenarios
Ship counts scenarios passed when their milestone was delivered. Final counts them after later milestones, combining tests of the finished application with historical system checks recorded at the relevant milestone. Those historical checks are not rerun against the final code.
Recovery
The change from ship-time to final scenario totals. A positive value means later work repaired earlier failures; a negative value means regressions outnumbered repairs. Migration failures recorded at delivery still count even if the code is repaired later.

The runs

The Models view includes 73 runs that completed all seven milestones and passed the benchmark's integrity checks. Runs with low scores are included. Unfinished runs and runs with invalid evaluations are excluded. Each configuration has between one and five runs, so small differences in averages may not hold up with more samples. Chart ranges show the lowest and highest observed values, not confidence intervals.

A model runs through a coding tool, or harness, which also affects the result. Astra uses Codex CLI 0.153.4; earlier GPT runs used an older Codex version. The twelve Astra runs shown here, three each at low, medium, high and X-High, used the standard v6 handoff prompts and launched no subagents. Opus 5 uses Claude Code 2.1.243 with customizations disabled. Muse Spark uses OpenCode 1.18.27; the harness comparison uses OpenCode 1.18.0.

Astra X-High runs 2 and 3 stopped on provider-capacity errors, then completed after restarting the interrupted milestone from the last accepted snapshot. No evaluation feedback was supplied. Their costs and runtimes include the discarded attempts; the time between stopping and restarting is excluded. The Astra results document both resumptions.

The Harnesses view includes 20 of the Codex runs from the Models view, 20 additional OpenCode runs and five Luna runs with the delegation instruction. There are 45 runs in that view, but 20 also appear in Models.

Cost accounting

Codex and Claude Code costs are API-equivalent: recorded token usage multiplied by the documented API rates. These runs used subscriptions, so the amounts are comparison costs, not additional subscription charges. OpenCode model costs are recorded OpenRouter charges, except GLM-5.3 Flash, whose free-preview usage is priced at its production rates. The Harnesses view uses API-equivalent costs throughout.

Costs include the main agent and all its subagents, as well as Codex's automatic review, priced at Luna rates. Reasoning tokens are included in output tokens and are charged only once. The private evaluator makes no model calls and adds no inference cost.

In the Astra runs shown here, the largest request contained 123,779 input tokens, below the 272K threshold for long-context pricing, and no cache-write tokens were recorded. GPT-5.5's recorded context window was 258,400 tokens. Some older logs lack enough detail to reconstruct per-request surcharges or cache-write charges, so those estimates use standard rates.

Codex includes cache reads in its total input count; OpenCode reports them separately. The calculations account for that difference. As an agent's conversation grows, repeatedly sending its history can become expensive even at cached rates: cache reads account for roughly $12–14 per Kimi run and $13–22 per GLM 5.3 run.

Model-specific accounting

GLM-5.3 Flash was tested as OX Alpha, a free preview. Its displayed costs apply the announced production rates to that preview usage. The two Opus subscription runs recorded $43.96 and $51.35 in API-equivalent usage. The OpenCode harness comparison used a subscription login and incurred no additional inference charges.

Muse Spark's $53.61 charge includes two automatic continuations after it reached the turn-length limit. DeepSeek run 2 includes $0.32 for a repeated review that made no code changes.

Code size and runtime

Code size counts lines in the finished application, including comments and blank lines. Production code covers lib/ and database migrations; test code covers test/. The table shows the median across runs, rounded to a whole line. Line counts describe the size of the implementation, not its quality.

Runtime adds up the time spent in agent sessions across the seven milestones, including reasoning, tool use, tests, continuations and interrupted attempts in completed runs. Time spent running the private evaluator, saving snapshots or advancing to the next milestone is excluded. The two resumed Astra X-High runs exclude stopped time. DeepSeek run 4 also excludes a documented 10h 52m machine interruption; time spent working before and after it is retained.

Subagents counts distinct agents started by the candidate. Built-in workers such as Codex's automatic reviewer are excluded from that count, but their token usage is included in the cost.
